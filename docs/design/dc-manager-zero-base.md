# DC NOW — 담당자 중심 제로베이스 화면 설계

설계 목적: 국내 데이터센터 현황을 조사·갱신·검토하는 담당자의 일일 업무를 하나의 관리 작업공간으로 연결한다.
이번 산출물은 새 정보 구조와 탐색 가능한 화면 시안이다. 시안의 센터명·수치·변경 내용은 설계용 예시이며 실제 데이터 확정이나 승인을 실행하지 않는다.

## 1. 담당자가 매일 답해야 할 질문

- 관리 대상 중 운영 중인 센터와 개발 중인 프로젝트는 각각 무엇인가?
- 어제 이후 어느 센터의 용량·RFS·전력·사업자가 바뀌었는가?
- 이번 주에 확인해야 할 근거와 일정은 무엇인가?
- 근거가 충돌하거나 너무 오래된 값은 무엇인가?
- 확정한 변경이 원장, 지도, 공급 분석, 공개 화면에 반영됐는가?

첫 화면은 `오늘의 업무`다. 뉴스 수와 수집 문서 수는 센터 현황을 관리하는 업무의 보조 지표다. 센터에 연결되지 않은 문서는 별도 분류함에서 처리한다.

## 2. 새 탐색 구조

| 메뉴 | 목적 | 대표 행동 |
|---|---|---|
| 오늘의 업무 | 변경·충돌·기한 초과 업무와 현황을 함께 확인 | 담당 업무 열기, 근거 비교, 처리 후 다음 건 이동 |
| 센터 현황 | 운영·개발·병행·보류 센터를 같은 기준으로 관리 | 검색, 필터, 정렬, 상세, 비교 |
| 개발 프로젝트 | 센터별 프로젝트·Phase·공정·RFS 관리 | 단계 변경 검토, 예정일 확인, 증설 연결 |
| 지도·지역 | 위치·개발 집중·전력 규모 확인 | 목록과 지도 동기 선택, 좌표 보완 |
| 공급 분석 | Phase별 RFS와 IT Load를 기준으로 전망 | 기준 시점 선택, 확정·추정 분리, 원장으로 이동 |
| 사업자 | 운영사·개발사·소유주·투자자·운용사·시공사 관계 관리 | 사업자 선택, 역할별 포트폴리오 보기 |
| 변경 검토 | 기존값과 제안값을 근거로 비교 | 승인, 수정 후 승인, 보류, 반려, 중복 |
| 수집·발행 | 수집부터 공개 반영까지 처리 단계 확인 | 실패 복구, 미분류 문서 확인, 발행 확인 |

센터 상세는 어느 화면에서나 같은 작업공간으로 열린다. `센터 현황 → 상세 → 근거 검토 → 반영 확인`으로 이동해도 필터와 목록 위치를 보존한다.

## 3. 공통 화면 규칙

- 상단: 통합 검색, 마지막 수집 시각, 원장 변경 시각, 공개 발행 시각.
- 왼쪽: 오늘의 업무 / 센터·프로젝트 / 조사·검토 / 운영 메뉴.
- 본문: 화면별 로컬 필터와 결과. 각 집계의 기준 범위를 바로 옆에 표시.
- 오른쪽: 선택 센터 또는 변경 건의 상세. 넓은 화면에서는 비교하면서 작업.
- 하단 작업 영역: 현재 변경의 처리 결과와 다음 작업. 저장 실패 시 입력 유지.
- 필터는 실제 조회에 적용되는 선택만 보여준다. 작동하지 않는 장식용 필터는 배치하지 않는다.
- 주요 표는 14px 이상, 보조 문구는 12px 이상. 8px 이하 축약 텍스트는 사용하지 않는다.

## 4. 기본 단위와 상태

시설 범주, 개발 단계, 검토 상태, 최신성을 서로 다른 데이터로 다룬다.

| 축 | 값 | 용도 |
|---|---|---|
| 시설 범주 | 상용 / 클라우드·IT 자체 / 기업 전용 / 공공 / 미확인 | 시장 공급 집계 범위 |
| 개발 단계 | 계획 / 인허가 / 착공 / 건설 / RFS / 운영 / 보류 / 종료 | 센터 및 Phase의 현재 상태 |
| 근거 상태 | 확정 / 제안 / 충돌 / 미확인 | 필드별 판단 가능 범위 |
| 최신성 | 최근 확인 / 확인 기한 도래 / 기한 초과 | 추가 조사 업무 |
| 위치 정밀도 | 건물 / 도로 / 필지 / 행정구역 / 미확인 | 지도 표시 신뢰도 |

운영·개발 병행 캠퍼스는 센터 수에서 1개로 센다. 운영 용량과 미래 Phase 용량은 따로 집계한다. 후보 센터는 모두 검색할 수 있으나 확정된 시장 공급에는 넣지 않는다.

## 5. 화면 A — 오늘의 업무

### 기본 배치

1. 페이지 제목과 마지막 확인 시각.
2. 관리 범위 선택: 상용, 자체 사용, 기업 전용, 전체 추적.
3. 현황 요약: 운영 센터 / 개발 프로젝트 / 변경 검토 / 확인 기한 초과.
4. 중심 영역 70%: `오늘 처리할 변경` 표.
5. 오른쪽 30%: `누락·최신성 확인`과 `수집·공개 반영 상태`.
6. 아래: 운영·개발 대상의 최근 변경 목록. 행 선택 시 센터 상세.

### 작업 표

센터명, 변경 항목, 현재값, 제안값, 영향, 근거 수, 검토 기한, 담당자.
우선순위는 공급량·RFS·전력·운영 상태에 영향을 주는 변경, 근거 충돌, 기한 초과, 일반 보완 순이다. 실제 기한과 담당자가 없으면 임의 날짜나 이름을 채우지 않고 `미지정`으로 표시한다.

상태 전환 후 처리 건이 실제로 줄었는지, 원장 값이 바뀌었는지, 공개 발행이 완료됐는지까지 보여준다.

## 6. 화면 B — 센터 현황

### 목록이 기본, 지도는 보조

목록·지도 전환에서 동일한 필터와 선택 센터를 유지한다. 최초 목록은 운영·개발을 모두 표시한다. 캠퍼스 아래 건물과 Phase를 펼칠 수 있다.

기본 열: 센터 / 단계 / 지역 / 운영사 / 운영 IT Load / 개발 IT Load / 수전용량 / 다음 RFS / 확인 상태 / 마지막 확인.
보조 열: Owner, Developer, Investor, Asset Manager, 시공사, GPU/DLC, 가용용량, 담당자.

- 단계별 탭: 전체, 운영, 개발, 운영·증설 병행, 보류, 미확인.
- 범주 필터: 상용, 자체 사용, 기업 전용, 검토 후보.
- 저장 보기: 수도권 개발, 2028 RFS, 용량 미확인, 이번 주 확인 대상.
- 정렬: RFS 가까운 순, 마지막 확인 오래된 순, 운영 IT Load 큰 순.
- 비교: 2~5개를 선택하고 부족한 필드가 어떤 것인지 함께 확인.
- 상세 주소와 좌표를 독립 표시. 행정구역 중심점은 정확 위치처럼 보이지 않게 한다.

## 7. 화면 C — 센터 작업공간

상단에 센터명, 시설 범주, 단계, 지역, 확인일을 표시한다. 같은 센터에 운영과 개발이 존재하면 Phase별 구성을 함께 노출한다.

### 첫 탭: 현황

- 상단 수치: 운영 IT Load, 개발 IT Load, 수전용량, 다음 RFS.
- 중앙: 캠퍼스 → 프로젝트 → Phase 구조와 각 용량·RFS.
- 오른쪽: 확인해야 할 정보와 최근 변경.
- 아래: 운영사·소유주·개발사·투자자·운용사·시공사 역할 관계.

### 나머지 탭

| 탭 | 표시 데이터 |
|---|---|
| 프로젝트·Phase | 개발 단계, 단계별 용량, RFS 분기, 일정 근거 |
| 전력·시설 | 수전용량·계약전력·전압·변전소·PUE·냉각·밀도·GPU/DLC |
| 사업자·고객 | 관계 역할, Tenant, 고객 요구, LOI·계약, 정보 공개 범위 |
| 근거·이력 | 값별 근거, 확인일, 변경 전후, 승인·반영 이력 |

모든 값 옆의 근거 버튼은 문서와 해당 문장·표·페이지로 연결한다. 데이터 확보 전에는 확인 필요 표시와 조사 업무 생성 기능을 제공한다.

## 8. 화면 D — 변경 검토

### 세 영역을 동시에 표시

- 왼쪽: 센터별 변경 묶음과 영향·긴급도.
- 중앙: 현재 확정값 → 신규 제안값. 단위, 기준, 시점, Phase 범위를 나란히 비교.
- 오른쪽: 근거 문서, 출처 유형, 발행일, 추출 원문, 상충 근거.

### 처리 규칙

1. 원문과 센터 연결을 확인한다.
2. 수전용량/IT Load/발표용량 및 캠퍼스/Phase 범위가 같은지 확인한다.
3. 사유를 작성하고 승인 또는 수정 후 승인한다.
4. 변경 이력과 원장 반영을 같은 트랜잭션에서 기록한다.
5. 영향받은 지도·공급 분석을 재계산한다.
6. 공개 발행은 별도 상태로 보여준다.

문서 승인만으로 개별 필드를 확정하지 않는다. 값이 변경된 뒤 다른 검토자가 오래된 화면으로 승인하면 충돌 경고를 제공한다. 캠퍼스와 Phase 용량은 중복 반영을 막는다.

`원장 반영 완료`, `공개 발행 대기`, `공개 반영 완료`를 구분한다. 시안의 승인 동작은 설계용 로컬 모의 동작으로 제한한다.

## 9. 화면 E — 공급 분석

- 기본 범위: 확정된 상용 공급.
- 기준: IT Load. 수전용량과 발표용량은 별도 선택.
- 시간: 현재 운영 누적 / 분기별 미래 신규 / 연말 누적.
- 확정·추정·일정 미확인을 분리한다.
- 차트 클릭 시 해당 지역·사업자·Phase 목록으로 내려간다.
- 원장에 없는 가용용량은 `미확인`으로 표시한다.

`가용용량 = IT Load − 계약 − LOI`는 동일 범위·동일 시점에 확인된 값이고 계약/LOI 중복이 제거된 경우에만 계산한다. 캠퍼스 전체 발표용량을 Phase의 IT Load로 대체하지 않는다.

## 10. 지도 설계

Google Maps 위에 검증된 좌표를 실제 마커로 표시하는 화면을 목표로 한다. 기존 검색 iframe은 선택한 주소를 조회하는 방식이므로, DB의 전체 센터 마커 지도와 구분해야 한다.

- 좌측: 검색 결과와 좌표 미확인 목록.
- 중앙: Google 지도, 단계별 마커, 클러스터.
- 우측: 선택 센터 요약과 근거/상세 접근.
- 크기: 확인된 IT Load를 선택적으로 반영. 값 미확인은 고정 크기와 라벨.
- 같은 캠퍼스의 건물·Phase는 캠퍼스 하나로 묶고 펼치기.
- 정확 위치가 없는 대상은 행정구역 표시와 정밀도 라벨, 또는 미확인 목록으로 표시.

다중 마커 Google 지도 구현에는 Google Maps JavaScript API 구성과 도메인 제한 설정이 필요하다. 지도 로드 실패 시 같은 결과 목록을 유지한다.

## 11. 수집·발행 흐름

수집 문서 → 중복 제거 → 센터/사업자 연결 → 필드 추출 → 변경 비교 → 검토 → 원장 반영 → 공개 발행.

각 단계에서 마지막 성공 시각과 대기 건수를 표시한다. 수집 성공을 공개 갱신 성공처럼 표시하지 않는다. 최근 실행 상태뿐 아니라 현재 시각과 실행 주기에 따른 지연도 확인한다.

일일 이메일은 새 문서 개수에 더해 신규 센터, 확정 변경, 남은 중요 검토, 공개 발행 시각을 중심으로 보고한다.

## 12. 데이터 품질 표현

하나의 백분율 대신 관리에 필요한 질문을 제시한다.

- 용량 산출에 사용할 수 있는 센터는 몇 개인가?
- RFS 기준 전망에 포함할 Phase는 몇 개인가?
- 좌표가 검증된 센터는 몇 개인가?
- 운영 단계가 근거로 확인된 센터는 몇 개인가?
- 마지막 확인일이 기한을 넘긴 필드는 무엇인가?

필드별 확인일과 실제 자료 발행일을 분리한다. DB 업데이트 시각은 확인일로 대체하지 않는다. 이력 자료가 오래됐다는 이유만으로 폐기하지 않고 현재값 근거의 재확인 필요 여부를 판단한다.

## 13. 현재 기능과 개발 간격

| 영역 | 로컬 코드에서 확인한 상태 | 새 설계에 필요한 작업 |
|---|---|---|
| 센터 현황 | 시설 범주, 운영·개발, 위치, 사업자, 일부 용량/RFS 제공 | 캠퍼스/Phase 표현, 저장 보기, 정렬, 상세 편집 |
| 근거 검토 | 내부 API에서 7개 Entity 승인·반려 및 감사 기록 | 필드별 전후 비교, 수정·보류·중복, 동시 수정 충돌, 원장 연결 |
| 품질 | 누락·관계·용량·근거 날짜 점검 | 필드별 확인일과 담당 업무·기한 |
| 공급 | 연도별 집계와 일부 프로젝트/용량 | 분기별 Phase 합산과 중복 제거, 자료별 확정/추정 |
| 지도 | Google 검색 iframe과 센터 목록 | 검증 좌표의 다중 마커, 클러스터, 목록 연동 |
| 수집·게시 | systemd 수집과 정적 사이트 게시 코드 | 단계별 상태, 미분류 문서, 승인 후 발행 추적 |
| 고객·계약 | 공개 대시보드에 준비 화면 | 권한과 내부 데이터를 연결한 조회/입력 및 계산 |

승인 API는 로컬 내부 서버에 있고 인증이 필요하다. GitHub Pages의 공개 정적 사이트는 조회용 화면이다. 담당자의 쓰기 작업은 인증된 관리 API에 연결된 관리 화면으로 구현한다. 공개 배포 자료에 내부 검토 큐나 고객 계약 정보를 넣지 않는다.

## 14. 개발 순서와 완료 기준

### 먼저: 센터 현황과 상세

검색·상태 필터·센터 상세·Phase·근거·이력을 실제 데이터에 연결한다.
완료 기준: 어느 센터의 현재 운영과 증설 상태, 용량 근거, 마지막 확인이 한 화면에서 설명된다.

### 다음: 담당 업무와 변경 검토

변경 제안과 현재값 비교, 담당자·기한, 승인·반영·공개 발행 추적을 연결한다.
완료 기준: 새 RFS 근거 하나를 검토하면 해당 Phase 일정과 공급 전망, 공개 반영 상태까지 확인된다.

### 다음: 지도와 공급 분석

확정 좌표의 다중 마커, 분기별 IT Load, 지역/사업자 필터와 원장 이동을 구현한다.
완료 기준: 특정 연도·지역 공급량을 선택하면 그 합계를 구성하는 Phase와 근거가 모두 나온다.

### 이후: 고객·계약과 사업개발

권한별 상업 정보를 연결하고 동일 범위·시점의 가용용량을 산출한다.
완료 기준: 고객 요구조건에 대한 후보센터와 값의 미확인 사유를 설명한다.

## 15. 시안 확인 방법

대화 내 시안에서 오늘의 업무, 센터 현황, 센터 상세, 변경 검토, 공급 분석을 전환할 수 있다.
센터 행 선택, 운영/개발 필터, 검토 모의 승인으로 업무 흐름을 확인한다. 실제 API 요청이나 데이터 저장·이메일·배포는 수행하지 않는다.

## 16. 시안 검증

브라우저에서 오늘의 업무 → 센터 현황 → 상세 → 변경 검토 → 공급 분석 탐색을 확인했다.
개발 단계 필터·지역 검색·센터 선택이 정상 동작한다. 모의 승인 후 센터 A 운영 IT Load가 20→24 MW, 총 운영 공급이 32→36 MW로 바뀌며, 센터 B의 RFS 제안 승인 시 2028 Q2→Q4로 표시된다. 데스크톱 1024px 및 모바일 390px에서 검사했고 외부 가로 넘침과 JavaScript 실행 오류가 없었다.
